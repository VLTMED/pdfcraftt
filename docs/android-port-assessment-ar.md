# تقييم جدوى نقل PdfCraft إلى Android

**تاريخ التدقيق:** 2026-10-12
**المصدر:** المستودع `VLTMED/pdfcraftt`، commit `84a75eae1b46d155656f10e9278373726a808fbb` (مطابق للأرشيف المرفق).
**المنهج:** يبدأ هذا التقرير بخط أساس ساكن للمصدر عند commit المذكور، ثم أُضيف تحديث للتنفيذ في هذا الفرع. في 2026-10-12 نجحت اختبارات المضيف لجسر Android (3 اختبارات)، بينما فشل Clippy الصارم بسبب lint قائم في `crates/engine/src/camera_edges.rs:235` (`manual_range_contains`)؛ بناء Gradle للنسخة الحالية واختبارات الأجهزة لم يثبتا بعد.

## الحكم التنفيذي

يمكن إعادة استخدام أجزاء كبيرة من محرك PDF المكتوب بـRust؛ فالمعمارية تفصل طبقات COS/model/render/edit/engine عن واجهة egui في الطبقات الأدنى (`docs/architecture.md:24-36`). لكن المستودع الحالي **لا يحتوي تطبيق Android أو Kotlin/Gradle/Manifest أو JNI/NDK أو بناء APK**؛ واجهاته القائمة هي تطبيق سطح مكتب، CLI، وواجهة WebAssembly.

وعليه: **نقل الوظائف الموجودة إلى Android قابل للتنفيذ هندسياً، لكن التكافؤ الكامل غير مثبت ولا يمكن الادعاء به قبل تنفيذ واختبار كل وظيفة على أجهزة ومجموعة ملفات مرجعية.** كان upstream عند commit المصدر بلا مشروع Android؛ أما هذا الفرع فيضيف تطبيق Compose وجسر Rust/JNI قيد التطوير، ولا يحوّل ذلك وحده الحالة إلى تكافؤ. كما أن المشروع نفسه يصف مرحلته Alpha (`ROADMAP.md:1-6`) ويذكر فجوات قائمة، منها عدم اكتمال renderer الداخلي وقياس fidelity، وحدود تحرير المحتوى والخطوط، ومحدودية OCR والتحويلات والتوقيعات (`ROADMAP.md:32-76`). نقل الموجود لا يكمّل تلقائياً ما هو جزئي في الأصل.

## ما يثبته المصدر وما لا يثبته

- **تحليل PDF:** توجد طبقة COS لتحليل الكائنات/xref وإصلاحه والتشفير والحفظ التزايدي والكامل (`crates/cos` و`crates/crypt`). لكنها تحتفظ بمصدر المستند كاملاً في الذاكرة، ولا تعني وحدها أن جميع صيغ الصور أو ملفات PDF المعقدة مدعومة بالكامل.
- **العرض:** التصيير الحالي CPU عبر hayro/vello_cpu مع patches وقيود موارد (`crates/render`, `docs/architecture.md:56-68`). يذكر التوثيق أن renderer الخاص ومحرك الخطوط وقياس التكافؤ ما زالت أعمالاً لاحقة.
- **التحرير والتعليقات والنماذج والتنظيم:** توجد وحدات Rust واختبارات فعلية للتعليقات والنماذج وتنظيم الصفحات والتحرير والحفظ/إعادة الفتح والتراجع. لكن وجود API أو اختبار محدد لا يثبت تكافؤ كل ملفات Acrobat؛ توثيق المشروع يذكر قيوداً في تحرير الخطوط/المحتوى وXFA/JavaScript وبعض حالات التوقيع.
- **OCR والتحويل:** توجد وظيفة OCR محلية تعتمد نماذج، لكن النطاق اللغوي والتحويلات وصيغ Office ليست كاملة؛ Office import غير موجود وبعض التصدير محدود (`docs/file-format-parity.md`, `docs/gaps.md`, `crates/ocr`).
- **Android:** لا توجد نقطة دخول Activity، طبقة SAF/Content URI، دعم لمس/IME/TalkBack، أو CI خاص بـAndroid في النسخة المدققة. هذه أعمال نقل جديدة وليست قدرات موروثة تلقائياً.

الأرقام في `ROADMAP.md` (نحو 67% من عرض الميزات tier-weighted ونحو 49% جاهزية مقدرة للعمل الكامل) تصف حالة PdfCraft الحالية لا Android، وهي ليست دليلاً على تكافؤ شامل.

## المعمارية المقترحة

1. **نواة Rust مشتركة:** إعادة استخدام طبقات PDF التي تنجح في cross-build؛ إبقاء parsing/render/edit/forms/annotations/security خارج Kotlin، وعدم إعادة كتابة المحرك في واجهة Compose.
2. **جسر Android مستقل:** crate JNI/UniFFI بواجهة ABI ثابتة ومحدودة للفتح/الإغلاق، الأخطاء وكلمات المرور، البحث والرندر والتحرير والتقدم والإلغاء والحفظ. لا تكشف هياكل Rust الداخلية إلى Kotlin.
3. **واجهة Android أصلية:** Jetpack Compose/Material 3 مع Activity lifecycle، عمليات خلفية، إيماءات لمس/قلم، IME وإتاحة الوصول. تُفصل عن واجهة egui المكتبية.
4. **تكامل الملفات:** استخدام Storage Access Framework وContent URI وصلاحيات URI المستمرة وكتابة ذرية ومشاركة النظام؛ لا يُفترض أن URI مسار ملف عادي. يلزم قياس ذاكرة المستندات الكبيرة ومعالجة الإلغاء والاستعادة.
5. **الرسم:** ابدأ بمسار CPU/tile مع حدود ذاكرة واختبارات جودة. أضف GPU Android بعد التحقق من دورة حياة السطح والأداء والحرارة على أجهزة حقيقية؛ wgpu الحالي يرسم واجهة التطبيق أساساً، لا صفحة PDF مباشرة.
6. **التوافق والبناء:** CI لـ`arm64-v8a` و`x86_64`، اختبارات Android instrumentation وGolden/interoperability، مع artifacts واضحة. APK debug ليس إصداراً إنتاجياً موقعاً.

## تعريف عملي لـ«0% تضحية»

تُقاس المساواة مع **كل وظيفة موجودة فعلياً في commit المصدر المحدد**: المدخلات، المخرجات، الأخطاء، كلمات المرور، حفظ/إعادة فتح، الدقة، الصلاحيات، undo/redo والتبادل مع قارئات أخرى. تكييف واجهة الاستخدام مسموح؛ لكنه ليس دليلاً على تطابق النتيجة.

يجب فصل هدفين مختلفين: **تكافؤ مع تنفيذ PdfCraft الحالي** هدف قابل للاختبار؛ أما **تكافؤ كامل مع Acrobat أو مع قائمة ميزات أوسع من الموجود في PdfCraft** فيتطلب أولاً إكمال فجوات الأصل. لا يوجد الآن Android build أو baseline بصري/وظيفي شامل أو قياس side-by-side كافٍ لإثبات ادعاء 100%.

## المخاطر التي يجب أن تبقى ظاهرة

- عدم وجود هدف Android مُختبر؛ قد تتطلب اعتماديات Rust العابرة فصل shell أو تهيئة NDK/features إضافية.
- مستندات PDF والـraster/caches تستهلك ذاكرة الهاتف؛ القراءة الحالية ليست streaming كاملة.
- renderer والخطوط غير مكتملين/غير مقاسين على كل الحالات، وبعض الفلاتر تعتمد على renderer خارجي.
- جسر Android الحالي يستخدم مساحة Automation مستمرة متعددة المستندات بدلاً من إعادة تحليل الملف لكل طلب؛ لكن العرض ما زال صورة صفحة كاملة بمقياس ثابت، بلا tile/cache/zoom عالي الدقة، ويلزم قياس الذاكرة والأداء قبل توسيع هذا المسار.
- SAF وURI permissions ودورة حياة التطبيق والدوران وprocess death واللمس وIME وTalkBack والطباعة/المشاركة تحتاج تنفيذ Android واختبارات مستقلة.
- redaction والتشفير والتوقيع تحتاج مراجعة أمنية لمسارات full-save والملفات المؤقتة وكلمات المرور وKeystore.
- وجود أسماء اختبارات أو parity checklist لا يثبت أن الاختبارات شُغّلت أو أن الأداء/المخرجات مطابقة بصرياً.

## شريحة التكامل في هذا الفرع

يتضمن الفرع الآن تطبيق Compose وجسر JNI إلى مساحة Automation مستمرة، وإدخال SAF مرحلياً، فتحاً بكلمة مرور، عارض الصفحات والتنقل، البحث الأساسي، undo/redo والحفظ incremental/full بنقل مجزّأ، تصديراً، ونماذج JSON Schema للأدوات الـ153. أُضيف كذلك تبويب يسرد سجل الأوامر الـ190؛ منه 62 لها ربط Automation صريح، و128 بلا ربط مباشر، وتظل الأوامر غير المنفذة معلّمة ولا تُحسب تكافؤاً. العرض الحالي full-page bitmap وليس tiled/zoom متقدماً؛ كما أن Compose والـNDK/APK لهذه الشريحة الموسعة لم يجتازا بعد بناء Android على CI أو instrumentation. اختبارات Rust للمضيف نجحت (3/3)، وهذا لا يثبت الوظائف الطرفية أو جودة APK.

### جرد الأوامر ومقياس التكافؤ

المصدر يعرّف **153 أداة Automation فريدة** و**190 أمراً مسجلاً**. يملك `command_run` حالياً ربطاً صريحاً لـ**62** أمراً، ويرفض **128** أمراً لغياب أداة مباشرة. لذلك لا يكفي عرض نماذج الأدوات للقول إن وظائف الواجهة انتقلت؛ كل صف في [جرد الأوامر الكامل](android-command-coverage-ar.md) يحتاج إما معالج Android أصلياً أو أداة Rust مطابقة واختباراً. لم تُحسب نسبة تكافؤ كلية.


## ملاحظة تنفيذ CI

فشل تشغيل Android الأول لأن إعداد SDK الافتراضي طلب الحزمة القديمة `tools` التي لم تعد متاحة. تُشير [وثائق الإجراء الرسمية setup-android](https://github.com/android-actions/setup-android) إلى إزالة الحزمة القديمة؛ لذلك يحدد workflow الحالي `android-actions/setup-android@v4` مع `packages: platform-tools` ثم يثبت المنصة وBuild Tools وNDK صراحة عبر `sdkmanager`. نجح بناء سابق للعارض الضيق قبل إدخال مساحة Automation الحالية؛ إعادة بناء APK للنسخة الحالية ما زالت مطلوبة. هذه ملاحظة تخص بيئة CI فقط ولا تثبت تكافؤ ميزات التطبيق.
